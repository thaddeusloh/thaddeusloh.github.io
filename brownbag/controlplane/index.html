The harness, one click at a time

The loop is the whole trick.

A model is a text-in, text-out function. It has no hands, no memory between calls, and no way to check anything. Everything that makes it feel like an agent is a loop somebody built around it. Step through one.

Notice what the model never did. It never opened anything, never remembered anything, and never decided the job was over. It only ever read a note and wrote a note back. Harness engineering is the craft of designing everything in that loop except the thinking.

Which end is which

The detail people reliably get backwards: the agent is the client and the system is the server. It reads the wrong way round, because the system sounds like the bigger thing. But a server is whoever offers abilities, and a client is whoever asks. Your harness holds the plug. The fridge holds the socket.

What MCP is not

Almost every argument about MCP comes from expecting it to do a job it was never meant to do.

  • Not the brain. MCP never decides that a tool should be used. The model proposes, the harness runs it. MCP only standardises how the asking and answering are shaped.
  • Not the loop. Take MCP away and you still have a harness — you just hand-write custom glue for every system, forever. MCP removes the glue, not the loop.
  • Not a replacement API. Your system already had an API. An MCP server is a thin standard wrapper in front of it that describes what's available in a form a model can discover and call at runtime.
  • Not the rulebook. MCP does not decide who is allowed to open which drawer, what it costs, or whether a human should approve first. That is the control plane's job, and it is the single most common mix-up.
  • Not agent-to-agent. MCP connects an agent to tools and data. One agent handing work to another agent is a different problem with different protocols. Same word "connect", completely different shape.

One flight up

The control plane never does the work.

A harness makes one agent good. A control plane makes a hundred agents governable. They are different floors of the same building, which is why "should we build a harness or a control plane" is the wrong question — you will end up with both, in that order.

  • Routing. Which model or which agent takes this job, given what it costs, how fast it must be, and how hard it is.
  • Identity. The agent is acting on somebody's behalf. Whose? An agent with no identity cannot be held to any rule.
  • Permission. Which sockets this agent may plug into, and which rows it may see once it's in. Enforced at retrieval, not by asking the model nicely.
  • Budget. Spend ceilings, rate limits, maximum steps. The loop that runs away is a cost incident, not a bug report.
  • Audit. Every prompt, tool call and result kept and replayable. If you cannot reconstruct what happened, you cannot answer the only question anyone will ask afterwards.
  • Rollout. Prompts and tool definitions are code. They need versions, canaries and a way back.
  • Escalation. The point where a human must approve before the action commits, decided by policy rather than by the agent's own confidence.
  • The stop button. One place to halt everything, that works even when the agents disagree.

In what order

You don't build all three at once.

One agent, one team, one task

Harness only. Spend the effort on context, tool design, stopping rules and an honest eval set. A control plane here is furniture nobody sits on.

Second app, or second system

Now MCP pays for itself, because the alternative is bespoke wiring that grows by multiplication. Add structured logging at the same time — it is much cheaper to start logging than to backfill it.

Several teams, real users, real money

Control plane. Routing, identity, entitlements, budgets, audit, escalation, stop button. The trigger is usually an incident, a regulator, or a bill — and all three arrive late.

The trap

Building a control plane before you have shipped one agent that works. You end up governing a system whose actual failure modes you have never seen, and every rule is a guess.
